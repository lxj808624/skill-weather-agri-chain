## 第 1 次核查（不通过）

**核查项：数据可得性与口径一致性。**

| 检查 | 结果 |
| --- | --- |
| 日线重复日期 | 0 |
| 日线 close 空值 | 0 |
| 日线 high<low 异常 | 0 |
| 天气面板行数 | 5783（2010-01-01 ~ 2025-10-31）|
| 归档预报实际可用起点 | 2018-01-01（符合设计）|
| 库存起点 | **2018-09-03** ← 与日线起点 2018-01-02 不一致 |
| 基差覆盖 | 1899 天，basis_ratio 无缺失 |
| 库存周期间隔中位 | 7 天，规律 |

**不通过理由（两条）**：

1. **样本天数差异未在报告正文披露**。库存从 2018-09 才开始，导致 B3 与 W 的样本内天数为 1051，比 B2 的 1155 少 104 天。报告表里只给了 n_is=1051，没有解释这个差的来源，读者会以为是有意剔除。**这是必须说明的口径事实**，否则「天气模型比基线差」可能被误读成「样本不同造成的」。
2. **2016-2017 归档预报温度为 0 占位值这件事，只写在 `config/regions.yaml` 注释里**，报告正文没有。这是数据陷阱，复跑者换年份就会踩到。

**整改**：

- §2.1 表格已补「库存 363 个周度点，2018-09 起」
- §2.2 已补「注意样本差」段落，明确 1051 vs 1155 的来源
- §2.1 已补「2016-2017 温度为 0 占位」，并在 §11 失败边界标明「2016-2017 样本不可用」

## 第 2 次核查（通过）

复查上述三处是否落实到正文：

- 库存起点：§2.1 表格已写「2018-09 起」；§2.2 已写样本差来源 → 落实
- 2016-2017 占位值：§2.1 已写；§11 已写「不可用」→ 落实
- 数据本身：无重复、无空值、无 high<low 异常 → 无问题

**结论：通过。** 数据层面无遗留问题。
